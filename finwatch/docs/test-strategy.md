# テスト戦略 — 3層構造

方針: **決定的な部分を最大化し、非決定的な部分(LLM)を最小の面積に隔離して統計的に検証する**(ADR-0009)。

## 層構成

| 層 | 対象 | 実行 | 判定 |
|---|---|---|---|
| L1 unit | resilience(breaker/retry/cache)、report純関数、redact、allowlist判定、budget計算 | 毎push、<10s | 決定的assert |
| L2 contract | MCPクライアント ⇔ モックMCPサーバー(スナップショット自動生成)。認証ヘッダ付与、セッション、エラー系(429/500/タイムアウト)、zodパース | 毎push | 決定的assert |
| L2' contract(実サーバー) | tools/listのスナップショットdiff(ADR-0008) | 日次cron | diff検知 |
| L3 eval | LLMのツール選択・引数生成の精度 | agent/prompts変更時 + 日次 | 統計的閾値90%、k=3試行 |

## 設計上のポイント

1. **LLM面積の最小化**: 数値の転記・表生成はLLM外の決定的コードで行う。LLMの責務は「どのツールを呼ぶか」と「解説文」のみ。→ テスト不能領域が構造的に小さい
2. **モックの現実追従**: モックサーバーはスキーマスナップショットから生成。手書きモックの陳腐化を防ぐ
3. **evalケースの資産化**: 本番で発見した誤動作は必ずevalケースに追加(リグレッション資産)。`evals/cases/` がプロダクト理解のドキュメントを兼ねる
4. **カバレッジ目標**: L1/L2対象コードでline 85%。ただし数値目標より「外部境界とセキュリティ制御(allowlist/redact)は100%」を優先
5. **CIパイプライン**: typecheck → lint → L1 → L2 →(条件付き)L3 → secret scanning。mainへのマージはすべてグリーンが条件
