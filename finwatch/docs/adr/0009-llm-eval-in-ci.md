# ADR-0009: LLM非決定性のテスト戦略 — evalの統計的閾値をCIゲート化

Status: Accepted / Date: 2026-07-02

## Context
「LLMが正しいツールを正しい引数で選ぶか」は非決定的で、従来のassert equalが成立しない。一方で無検証はリグレッションを見逃す。

## Decision
1. テストを3層に分離: **unit**(決定的ロジック) / **contract**(モックMCPとの通信) / **eval**(LLM挙動)
2. evalは `evals/cases/*.json` に「質問 → 期待ツール列 + 引数の述語(predicate)」を定義。完全一致ではなく述語判定(例: `codes contains E01379`)にして正解の多様性を許容
3. 判定は各ケースk=3試行、ケース合格= 2/3以上成功。**スイート合格閾値90%をCIゲート**とする(mainマージ条件)。閾値と根拠はこのADRで管理
4. コスト制御: evalはpushごとではなく、`agent/` `prompts/` 配下の変更時と日次のみ実行(ADR-0010)

## Alternatives
- **LLM-as-judgeによる出力品質評価**: レポート文面の質はjudge導入余地があるが、まずツール選択精度(客観判定可能)に限定。judge導入は将来ADR
- **温度0で決定性を仮定**: モデル更新で暗黙に壊れる。非決定性を前提にした統計的判定の方が頑健

## Consequences
- (+) 「プロンプト変更でツール選択精度が92%→71%に落ちた」をマージ前に検知できる
- (-) evalのフレーク対応(閾値ギリギリの揺れ)が残る → 失敗ケースの試行ログを必ずArtifact保存し、閾値調整はデータで議論
